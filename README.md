# typing-game

タイピングゲーム。汎用タイピング判定エンジンと、web UI。

## 雑なプロジェクトイメージ

- 面白い文言をタイピングさせたい
- ある文字のローマ字表記は多様なので難しいのは承知だが、ここでつまづくとゲームとして全然面白くないので、判定のクオリティにはこだわりたい
- 打つ文言をjsonとかで管理すると変更が困難なので、入稿と出題は分離しできると良さそう、レイヤはアプリケーション側の想定
  - 打つ文言はそれだけで整理・設計を要しそう（ここがつまらない・入稿しづらいと遊ばない・開発しない）なので、coreができてきたらちゃんとクオリティを上げたい

## core の設計方針

- UIを知らない
- パブリックインターフェースは絞る
- ローマ字入力や間違えた文字の扱いと、中核の判定ロジックは分離する
- アプリケーションレイヤとcoreの責務の境界が曖昧（タイピングはゲームでもありドメインそのものにも感じられる）なので、UIかcoreか迷ったら議論する
- core の中にもレイヤがある
  - 純粋に入力の検証
  - ローマ字のマッピング などなど

## テスト設計

- ユニットテストはパブリックインターフェース単位で書く
  - コードの分岐のカバレッジを意識する
  - ユニットテストでは、アプリケーションレイヤやオーケストレーション・ユースケースを意識したテストは書かず、純粋にpublic interfaceの仕様を検証する
- 統合テストは実際に書くときになったら議論し直したい
  - core 内のモジュール単位で書くか、core のパブリックインターフェース単位で書くか、など

## コードコメント

- AI によるコードコメントはコードの理解に役立たず、ファイルの肥大化を招く事態の方が多いため、AI はコードコメントを基本的に書かない
- 一般的なプラクティスによるコーディングの場合は、コードが意図を語るように実装すべき
- 例外として、どうしても一般的なプラクティスから逸脱する場合や、テスト内容をテストコードでどうしても正確に表せない場合は、WHY NOT コメントを書く
  - 例： // WHY NOT: 本来はxxxと書くべきだが、xxxのためにこうしている

## ファイル・変数などの命名

- プログラミング上の機能に寄せた名前ではなく、ドメイン上の意味に寄せた名前をつけたい
- 「xxxx.tsはゲームにおけるyyyyの機能です」、という説明をしなければ伝わらなかったり、「xxxxってなんですか？」という質問が出る時点で、ファイル名で語ることができていない
